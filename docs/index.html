把 Semi Design 复刻成 QML 组件库

源库是 Semi Design 官方 monorepo（ ~/Documents/Code/Html/semi-design）。目标是在现有的 semi.qml 工程里，用 Qt Quick 重建它的令牌体系与组件。下面是读完源库之后的评估、架构与分期计划，还没有写任何代码。

1 · 先看清工程量

源库不是"一个 React 组件库"那么简单，它是三层：semi-ui（React 渲染层）、semi-foundation（框架无关的状态机 + 组件样式）、semi-theme-default（设计令牌）。后两层才是复刻的主要参考物——TSX 提供 API 与行为，SCSS 提供视觉规格。

单看一个 Button，就知道复杂度在哪

Semi 的 Button 是 5 种主题色 × 4 种形态 × 4 种状态的笛卡尔积，再叠加 colorful（AI 渐变）变体和三档尺寸。它的 variables.scss 有 209 行，全部在展开这几十个色值组合：

维度 取值
主题色 type primary / secondary / tertiary / warning / danger
形态 theme solid / borderless / light / outline
状态 default / hover / active / disabled（另有 focus-visible 轮廓）
尺寸 size small 24px / default 32px / large 40px
附加 icon / loading / block / colorful / ButtonGroup / SplitButtonGroup
结论 像素级全量复刻是一个多人月量级的工程。合理的做法不是"照单全收"，而是先把令牌层和外观解析引擎做扎实，让后续每个组件都能复用同一套机制；然后按依赖顺序分期推进，每期都能独立交付、独立验收。

2 · 令牌体系：一条三层链

Semi 没有在组件里写死颜色。所有色值走的是三级引用，这是整个复刻里最需要先搬对的东西：

① 色阶
--semi-blue-5:
0,100,250
→
② 语义令牌
--semi-color-primary:
rgba(var(--semi-blue-5), 1)
→
③ 组件变量
$color-button_primary-
bg-default: var(--semi-color-primary)

色阶用 RGB 三元组存（0,100,250 而不是 #0064fa），因为组件层要靠 rgba(var(--semi-blue-5), 0.6) 这种写法临时调透明度。搬进 QML 时，色阶建议保留三元组形式，配色函数在 C++ 侧做。

16 个色系 × 10 级，明暗两套

下面是从 _palette.scss 直接解析出来的完整色板（实时渲染，鼠标悬停看 hex）。切到深色可以看到这套体系最关键、也最容易做错的性质： 暗色模式的色阶方向是整体反转的。grey 一行最直观——浅色下 grey-0 是 #f9f9f9，深色下是 #1c1f23，两套序列正好相反。

为什么这条很重要 色阶反转意味着「色阶 6 做文字、色阶 0 做底色」这类约定可以同时服务两种主题，同一个组件不必写两套颜色。反过来，如果按"浅色下越深越重"的直觉去映射暗色，对比度会全线崩掉。这条规律我在别的项目里踩过，这次要在地基阶段就用测试锁住。

动效到底在哪（已核对 npm 发布版） animation.scss 里所有 duration 确实都是 0ms，但这不是"值缺失"： semi-foundation 下 50 处组件级定义全部显式选用了 none 档，npm 上发布的 @douyinfe/semi-theme-default 与本仓库也逐字一致。也就是说交互控件的状态切换是刻意不做过渡的，反馈即时。真正的动画集中在弹层与进出场，而且不走令牌系统、直接硬编码：popover 100ms、modal 120ms（遮罩 90ms）、sidebar 180ms、notification 300ms、loading 旋转 600ms。另有一个 semi-animation 包承担 JS 插值动画。
完整清单 全部 383 个独立令牌（另有 40 个 AI 渐变的内部色标）的逐项明细 —— 含 Semi 默认值、明暗两套色块、引用关系与建议的 QML 字段名 —— 见 gallery 的 Tokens 设计变量 页（带搜索与点击复制色值），数据源与 src/SemiThemeValues.h 同源。

3 · QML 侧的架构

源库的三层（foundation 状态机 / SCSS 样式 / React 渲染）在 QML 里不能照搬，但结论可以借用： 把"该显示成什么样"从组件里抽出来，集中到一处。这是能否复刻几十个组件而不失控的分水岭。

模块结构

文件 职责
Theme（C++ 单例） 全部令牌：16×10 色板、语义色、尺寸、圆角、字体、阴影、z-index、动效时长。暴露 mode 切换明暗
Enums（C++） Variant / Size / Status / Placement / Direction 等枚举，替代 React 的字符串 props
Appearance（C++） 核心：把「组件 × 形态 × 状态」解析成具体色值，等价于 Semi 那几百行 variables.scss
ControlState（QML 基类） 统一采集 hovered / pressed / focused / disabled，组件不再各自接 handler
FocusRing（QML） 模拟 :focus-visible——只在键盘操作后显示焦点环
internal/ Popup 基座、图标基座、文本测量、动画曲线等公共设施
为什么要 Appearance 这一层 如果不抽这一层，Button 一个组件里就会散落几十个 if (variant === ... && state === ...)。有了它，每个组件只需要声明"我是 Button、我的色系是 danger、形态是 outline、当前是 hover"，色值由一处统一算出。这也是新增组件成本能压下来的原因。

三个绕不开的 QML 特性差异

  • 没有 CSS 变量继承——令牌靠 C++ 单例 + QML 属性绑定传递，组件不缓存色值，保证切主题时全局刷新。
  • 没有 :focus-visible——需要自己记录"最近一次交互是键盘还是指针"，否则鼠标点击也会弹出焦点环，视觉上比 Semi 脏。
  • 没有伪元素和 mixin——Semi 的 mixin.scss（shadow-0、文本截断、清除浮动等）要在 QML 侧用可复用的部件或 C++ 工具函数替代。

4 · 分期路线

按期推进，每期结束都有一个能跑、能验收的 Gallery。人日是按单人全职估的粗略量级，用于比较规模，不是承诺。

P0
地基 5–8 人日 · 无组件产出
完整 Theme 令牌 · Enums · Appearance 解析引擎 · ControlState · FocusRing · Popup 基座 · 图标基座（SVG + 着色）· Gallery 骨架（对照 semi.design 的分组导航）
验收：色板有单元测试锁住明暗两套共 320 个值与"暗色反转"性质；Gallery 能一键切换明暗；一个探针组件能正确响应全部状态与形态组合。
P1
基础控件 15–20 人日 · ~24 个
Button IconButton ButtonGroup SplitButtonGroup Input TextArea InputNumber Checkbox Radio Switch Tag Divider Space Typography Avatar Badge Spin Progress Skeleton Empty
验收：形态 × 状态矩阵逐项对照；键盘可达（Tab 顺序、空格/回车触发）；禁用态与只读态区分正确。
P2
容器与导航 15–20 人日 · ~18 个
Card Grid Layout Tabs Breadcrumb Steps Collapse SideSheet Navigation Anchor BackTop List Descriptions Timeline Divider

验收：Form 的校验状态机（校验触发时机、错误定位、跨字段依赖）与源库一致；日期选择器的键盘输入与日历面板双向同步。

5 · 难点与风险

按风险从高到低排。前四项会显著影响架构决策，不是"实现细节"。

01
Table 的虚拟化与固定列
QML 没有现成的"虚拟滚动 + 固定列 + 列宽拖拽 + 排序筛选"表格。需要自建一个 model/view 层，并用 TableView 或自绘 ListView 实现。这是整个项目里最重的单点。
02
弹层的定位与焦点管理
12 个方位自动翻转、边界碰撞检测、嵌套弹层的层级与关闭策略、Modal 的焦点陷阱与滚动锁定。Qt Quick 的 Popup 能提供基础，但策略层要自己写。
03
文本输入的原生细节
光标定位、选区、拖选、中文输入法（IME 预编辑）、撤销栈、TextArea 的自动高度。TextField 覆盖了大部分，但 PinCode、TagInput、InputNumber 这类需要自己接管键盘与光标。
04
focus-visible 的缺失
QML 只给 activeFocus，无法区分"鼠标点进来的焦点"和"键盘 Tab 进来的焦点"。需要一个全局的输入设备追踪器，否则所有鼠标点击都会带焦点环。
05
图标库规模
semi-icons 是数千个独立 SVG。全量移植不现实，建议先做按需引入的 SVG 着色机制，再挑常用的一批（约 80–120 个）落地，其余按需增补。
06
与 QtQuick.Controls 的取舍
复用 Controls.Basic 能白拿键盘导航、无障碍和 Popup 基座，但它的样式体系会和 Semi 的形态矩阵打架；完全自建则要重写这些基础设施。需要一个明确的边界——这是决策点之一。
07
动效默认值
源库把所有 duration 置为 0ms（见第 2 节的说明）。需要一个全局开关，并确认期望的默认观感。
08
RTL 与国际化
源库有 rtl.scss 和完整的 locale 体系（semi-ui/locale/）。建议先留出结构、不实现，避免后期返工。

6 · 待你拍板

这四点会实质改变计划的形状和代码结构，定了我就按它往下走。

Q1 复刻范围到哪一期？
▸
P0 + P1 + P2（推荐）
地基 + 约 42 个组件，35–48 人日。覆盖绝大多数后台界面，能形成完整的令牌与形态体系。
▸
只做 P0 + P1
20–28 人日，先把令牌与基础控件做扎实，验证机制是否成立再决定继续。
▸
全量到 P5
125–165 人日。需要接受这是一个长期工程，中途会有多个可交付节点。
Q2 保真度目标是什么？
▸
令牌与规格严格对齐，像素级近似（推荐）
色值、尺寸、间距、圆角全部取自源库；渲染差异（字体度量、阴影算法）允许存在。可对照截图验收。
▸
像素级像素对齐
逐像素比对截图。成本会翻倍，且字体渲染差异使得完全对齐不可达。
▸
神似即可
只借用设计语言，不追求规格一致。工作量最小，但"复刻"的意义会打折。
Q3 控件基座怎么选？
▸
视觉自建，复用 Qt 的输入与弹层基础设施（推荐）
外观全部自绘以对齐 Semi；键盘导航、IME、Popup 定位借 Qt 的成熟实现。平衡点最合理。
▸
完全自建
不依赖 QtQuick.Controls，控制力最强，但要自己重写焦点、IME 与弹层基础设施。
▸
基于 Controls.Basic 定制样式
起步最快，但 Semi 的形态矩阵与 Controls 的样式体系会持续冲突，后期改造代价高。
Q4 动效策略？
▸
严格跟随源库（推荐）
交互控件的状态切换不做过渡（即时反馈，与源库一致）；弹层与进出场按源库的硬编码值实现（popover 100 / modal 120 / sidebar 180 / notification 300ms）。图标走按需引入机制，先落地常用 100 个。
▸
交互控件也补上过渡
给 hover/active 加 100–200ms 过渡（即 animation.scss 里被注释掉的那套值），观感更柔和，但偏离源库。
▸
连弹层动画也省掉
动画全部归零，追求最朴素、最可预测的渲染表现。

7 · 现有脚手架怎么处置

上一轮搭的 semi.qml 骨架可以直接承接，不用推倒——但组件部分要按上面的架构重写。

现状 处置
CMake 工程 / 安装导出 / CMakePresets 保留已验证可被外部 find_package(Semi) 消费，直接沿用
测试基座（Qt Quick Test + ctest） 保留P0 的色板与形态矩阵测试就建在它上面
Gallery 应用 改造骨架保留，内容按 Semi 文档的分组导航重建
Theme 单例 重写当前只有 8 个颜色 + 9 个尺寸，要扩到完整令牌体系（含明暗反转语义）
Button / Card / Switch 重写当前是演示用的简化版，要按形态 × 状态矩阵重建
缺失的能力 新增Enums、Appearance、ControlState、FocusRing、internal/
